# 场景建筑拆分细化方案

> **GBE-Studio · 拆分层设计（ADR-0006）**
> 目的：解决「万安城要有几十上百栋中国传统建筑，而 AI 一次只能生成一整栋、整栋又完全不可复用」这个结构性问题。
> 契约部分（分级取值、插槽类型表、模数约束、装配清单格式、校验判据）见 `gbe-assets/docs/CONVENTIONS.md` **§9 / §19**；本文负责**工序、工具、粒度判据与落地排期**。
> 决策依据：`gbe-assets/docs/DECISIONS.md` **ADR-0006**。

---

## 0. 一句话

**不生成"建筑"，生成"构件"；建筑由装配清单拼出来。**

```
❌ 逐栋生成：万安城主殿 → 一栋 .glb（150k 面）→ 想改屋顶？重新生成一栋
✅ 构件化：45 类构件（檐柱/额枋/斗拱/瓦面/脊筒…）→ 装配清单引用它们
         想改屋顶？改一处引用 / 换一个构件版本，全城同形制的殿一起更新
```

## 1. 问题：为什么"一栋一生成"走不通

### 1.1 四个真实痛点

| 痛点 | 表现 |
|---|---|
| **不可复用** | 第 2 栋大殿要重新生成、重新精修、重新做 LOD/碰撞/材质——边际成本**恒等于首栋** |
| **风格发散** | 每栋独立生成，斗拱比例、瓦面密度、柱径、色彩都不同；"整城统一风格"变成纯手工美术活 |
| **不可修改** | 客户说"屋顶换成歇山"，只能重做一整栋 |
| **性能无梯度** | 整栋一个 mesh，LOD 只能整体降级——远景把斗拱糊掉、近景又不够精细 |

### 1.2 诚实的成本分析（这块必须先说清楚）

传统建筑恰恰是**人类最成熟的模块化体系之一**——"材分制 / 斗口制"就是古代的模数化标准。不利用这一点是浪费。但**构件化不是免费的**，先摆明代价：

**（a）生成成本：前期更贵，靠"边际收敛"回本**

| 阶段 | 逐栋生成 | 构件化 |
|---|---|---|
| 建库期（首批 45 类构件） | — | ≈ 24 × 30 + 3 × 55 = **885 credit**（18 件程序化件不花钱） |
| 每栋新建 | ≈ 55 credit | = 差异化构件数 × 30 credit |
| 第 1–10 栋累计 | 550 | 885 + 10×150 = **2385** |
| 第 11–25 栋累计 | 1375 | 2385 + 15×**N差**×30 |

> ⚠️ **这张表还没证明构件化更便宜，别把它当已结的账。** 按本表口径，即使 `N差` 在第 10 栋后就归零，25 栋时的生成 credit 仍是 **2385 vs 1375**——**单看 AI 调用费，25 栋内回不了本**。
> 真正的回报在 §1.1 的另外三项痛点里：复用意味着**精修、LOD 链、碰撞、材质、改型都不必重做**，而 credit 只是调用费、不含这些工时。要把这张表变成可信的决策依据，必须把「精修工时 / 返工率」折算进来重算——**已登记为待办，不在此处假装算过**。

> **关键假设（这是本方案最大的一笔赌注）**：随着构件库覆盖更多形制，**每栋新增的差异化构件数 `N差` 会从 5 收敛到 0–1**。
> 若 `N差` 长期停在 5，构件化的生成成本**永远追不平**——那时应当承认拆分失败，退回逐栋生成 + 手工 LOD。
> **验证点设在批 2 结束时**：若 8 类形制建完后，新建一栋仍需要 ≥4 件全新构件，则本方案判定失败（§11 回退方案）。

**（b）面数：LOD0 会上升约 3 倍，必须靠 LOD 链消化**

一栋歇山重檐大殿 LOD0 全开 ≈ 31 万面（檐柱 36k + 斗拱 160k + 瓦面 36k + 梁架 30k + 门窗 24k + 台基 8k + 装饰 20k），而逐栋生成的整栋模型约 10 万面。

| | 逐栋生成 | 构件化 |
|---|---|---|
| LOD0 | 100k | **~310k** ⚠️ |
| LOD1（中景） | 需自建 | **~78k**（构件级 LOD 链，斗拱单独降级） |
| 远景代理 | 需自建 | **~10k**（烘焙 + 减面，`derive --bake`） |

> 所以：**构件化在面数上不吃亏的前提是"LOD 链 + 远景代理是必需项，不是可选项"**。
> 但换来的是**局部降级能力**：远景时只有斗拱降级、主体轮廓仍清晰——整栋 LOD 做不到这件事。

**（c）真正的赢面：内存、可改性、可维护性**

- **内存**：25 栋建筑共享 45 份几何，而不是各存一份自己的。引擎的 instancing 让"同一构件出现 200 次"只占一份顶点数据。
- **可改性**：换屋顶样式 = 改一处引用；调柱径 = 改一件资产，全城生效。
- **可维护性**：LOD / 碰撞 / 材质 / 插槽是**库级一次性工作**，不是每栋重复劳动。

> 结论：**构件化的本质是"把一次性投入从每栋建筑搬到构件库"**。它在建筑数量少时更贵，在建筑数量多、同形制重复多时全面胜出。万安城（8 类形制 × 2–4 变体 ≈ 25 栋）正好落在胜出区间——但前提是形制真的能收敛。

## 2. 分层模型：L0 – L3

`granularity` 与 `tier` 是**正交**的两个维度（CONVENTIONS §3.1 / §19.1）：

- **`tier`** 说"做多好"（primitive / component / mass / hero）
- **`granularity`** 说"拆多细"（L0 / L1 / L2 / L3）

```
L0  整栋建筑 ────────────────── 五开间歇山重檐大殿
    │                           【只存装配清单，不存烘焙网格】
    │
    ├─ L1  部位 ─────────────── 台基 / 柱网 / 梁架 / 屋身 / 屋顶（上檐·下檐）
    │       │                   【可独立入库；通常是"半成品"，可再拆】
    │       │
    │       ├─ L2  构件 ─────── 檐柱 / 额枋 / 斗拱朵 / 瓦面 / 脊筒 / 墙段 / 格扇
    │       │                   【★ 主力产出，可复用最小单元】
    │       │
    │       └─ L3  装饰细部 ─── 鸱吻 / 垂兽 / 雀替 / 悬鱼 / 门钉
    │                           【挂接件，不参与结构对齐】
    │
    └─ 装配清单（assembly.json）── 引用 L1–L3 资产 + 插槽绑定 + 变换
```

| 层级 | `granularity` | `category` | 入库 | 面数参考 | 典型产出方式 |
|---|---|---|---|---|---|
| 整栋 | `L0` | `assemblies/building` | 只存清单 | — | 装配生成 |
| 部位 | `L1` | `components/*` | ✅ | ≤ `mass`（50k） | 路线 B 拆分 / 手工搭建 |
| **构件** | `L2` | `components/*` | ✅ | ≤ `component`（20k） | **路线 A 直生**（主力） |
| 装饰 | `L3` | `components/ornament` · `props/ritual` | ✅ | ≤ `component` | 路线 A / 程序化 |

> **L1 的定位要拿捏**：它是"为了方便拆分与运输"的中间层，不是最终复用单元。**能拆到 L2 就拆到 L2**——L1 的价值在于"整块替换"（比如整套屋顶换形制）。

## 3. 模数体系：让 AI 生成的构件真的能插上

### 3.1 为什么必须有模数

AI 生成的构件，尺寸是"看起来差不多"。两个构件的插槽位置差 3 cm，装配时就穿模或悬空。**模数网格是"跨生成批次的构件能互相插上"的唯一保证**——也是本方案里最不能妥协的一条。

中国古建本身就有模数体系（唐宋"材分制"、明清"斗口制"），我们把它**简化到米制**：

### 3.2 cn-ancient 模数表（真源 `kits/cn-ancient/kit.json` → `grid`）

| 含义 | 字段 | 值 | 用途 |
|---|---|---|---|
| 定位网格 | `snap_m` | **0.5 m** | 一切**插槽位置**与结构对齐（硬约束） |
| 造型网格 | `snap_m / 2` | **0.25 m** | 仅细部构件的**外部尺寸**（斗拱 / 门窗 / 脊件） |
| 墙宽模数 | `wall_module_m` | **2 m** | 墙段、开间的基本单位 |
| 层高 | `story_heights_m` | **3 / 4 m** | 竖向堆叠 |
| 柱距 | `pillar_spacing_m` | **2 / 4 m** | 柱网铺排 |
| 地砖 | `ground_tile_m` | **2 m** | 地面铺装 |

> **两级模数的纪律**：定位网格（0.5）用于插槽；造型网格（0.25）只用于尺寸。
> **插槽位置绝不允许用造型网格**——定位一松，跨构件拼装就散了（CONVENTIONS §19.2）。

### 3.3 尺寸推导示例（为 3 m 柱高的单檐殿）

```
地面 Y=0
  ├─ 台基：高 1.0 m（须弥座三层，每层 0.25 + 檐口 0.25）      → 台基顶 Y=1.0
  ├─ 柱础：高 0.25 m（覆盆）                                → 柱础顶 Y=1.25
  ├─ 檐柱：高 3.0 m（story_heights_m）                      → 柱头 Y=4.25
  ├─ 额枋：高 0.5 m（snap_m）                               → 额枋顶 Y=4.75
  ├─ 斗拱：高 1.0 m（3 层 × 0.25 造型网格，合计落 snap_m）    → 斗拱顶 Y=5.75
  └─ 屋顶：檐口起坡，举架 5 举 / 7 举 / 9 举
     檐出 1.5 m，正脊高 2.5 m（snap_m 整数倍）
```

**每一步的 Y 都落在 0.5 m 网格上**（1.0 / 1.25→*参见下注* / 4.25→*下注* / 4.75 / 5.75）。

> ⚠️ 注意：柱础顶 1.25、柱头 4.25 不在 0.5 网格上。
> **修正**：柱础高度应取 **0.5 m**（柱础顶 Y=1.5），柱高取 **3.0 m**（柱头 Y=4.5，落网格）。
> **规则**：**任何参与竖向堆叠（`stack-up` 插槽）的构件，其底面与顶面都必须落 `snap_m` 网格**。柱础是造型构件，但它的顶面必须落网格——所以柱础高度只能从 {0.5, 1.0} 里取值。这条纪律要在提示词与 QA 里同时体现。

让**AI 生成构件时优先走"结构尺寸由脚本强制、造型细节由 AI 自由"**的分工：柱高、柱径、斗拱层高由参数给定，AI 只负责纹样、瓦面密度、脊饰造型。

## 4. 拆分粒度判据：什么该拆、什么不该拆

拆得太粗 → 复用率低；拆得太细 → 构件数爆炸、装配爆炸、面数爆炸。五条判据：

| # | 判据 | 说明 |
|---|---|---|
| 1 | **复用次数 ≥ 2** | 预计全城只会出现 1 次的构件，**不拆**——没有复用就没有收益，只增加装配复杂度 |
| 2 | **结构可分离** | 有清晰的物理接缝（柱与础、斗拱与柱头、瓦面与椽）才拆；糊在一起的曲面（如整体曲面屋脊）不硬拆 |
| 3 | **材质同源** | 换材质时一起变的，留在同一个构件里（如"瓦面 + 檐口滴水"）；换材质会分家的，拆开 |
| 4 | **可替换性** | 会被独立替换的必须拆（门扇 / 窗扇 / 脊饰 / 瓦面）；永远一起出现的不拆（额枋 + 平板枋 可合并为"额枋组"） |
| 5 | **面数不失衡** | 单个构件面数不应超过其 tier 预算的 1/3（否则装配组合时面数失控）。斗拱这类高密度件，允许把"柱头科 / 平身科 / 转角科"拆成三种独立资产而非一种 |

**粒度计数器**（`gbe decompose report` 输出）：为每栋建筑算出「拆出的独特构件数 / 总实例数」（**复用比**）。经验目标：

- 复用比 **< 3**：拆粗了，考虑合并
- 复用比 **3 – 15**：健康区间
- 复用比 **> 20**：拆细了，考虑把若干构件合并（如整组门窗）

一栋歇山重檐大殿：独特构件 ≈ 45，总实例 ≈ 300 → **复用比 ≈ 6.7**，健康。

## 5. 路线 A：构件直生（主力）

**做法**：提示词**直接生成裸构件**，不生成建筑。

### 5.1 提示词结构（四段式）

```
[构件定义]  中国古代建筑屋顶构件——歇山顶单檐，仅屋顶本体
[拓扑计数]  1 主脊 + 4 垂脊 + 2 坡面 + 2 山花面；正脊两端各 1 鸱吻
[呈现约束]  悬浮独立呈现，正交多视角（前 / 侧 / 后 / 俯视）
[负向排除]  无墙体、无柱子、无台基、无地面、无场景、无人物、无文字、无背景
```

> 这套结构来自原型阶段已系统化的屋顶提示词体系（悬山 / 歇山 / 庑殿 / 攒尖 / 盝顶五样式），本方案把它**泛化到全部构件类别**。

### 5.2 批次审核机制（原型已验证，沿用）

1. **批量生成**（如 20 件一 批，含多视角）
2. **批量评审** → **只标记错误视角**（不是整件废弃）
3. **定向重生成**只针对错误视角
4. 合格件进 `raw/`，统一命名：`<asset-name>-<view>-<variant>.png`
5. 归档到 `generated-images/<批次>/`

> 关键：**只重生成错误视角**而不是整件重来——这是把成功率从"件"细化到"视角"的成本优化。

### 5.3 适用与不适用

| 适合路线 A | 不适合，转路线 B 或程序化 |
|---|---|
| 屋顶（五样式） | 整栋 hero 建筑（如主殿，需精确比例控制） |
| 柱 / 础 / 栏杆 / 墙段 | 结构关系复杂的重檐组合 |
| 门扇 / 窗扇 / 格扇 | 需要与既有建筑精确匹配的补件 |
| 脊饰 / 雀替 / 悬鱼等 L3 | — |

## 6. 路线 B：整栋拆分

**做法**：生成整栋 → 语义切分 → 得到构件 → 逐个精修 → 入库。

### 6.1 七道工序

```
① 整栋生成      提示词产整栋（优先 geometry-only 白模：拆件只需几何，不需要纹理）
                provider: hunyuan3d (tencentcloud 通道) 或 tripo
                ↓
② 语义标注      标记面选择集，标注来源：
                  材质槽 / 连通域 / 包围盒切面 / 手工涂选
                ↓
③ 几何切分      Blender 无头：bisect / separate / split by material
                → 产出候选构件团块
                ↓
④ 模数归一      每个团块：对齐主轴 → 吸附 snap_m 网格 → 包围盒归零
                超出容差的团块 → 进入 ⑦ 隔离
                ↓
⑤ 插槽推断      按构件类型推断插槽候选（见 §6.3），人工确认后写入
                ↓
⑥ 命名与 id     映射到 cn-ancient.<category-leaf>.<name>
                ★ 映射不出的部分 → ⑦ 隔离，禁止静默丢弃
                ↓
⑦ 隔离区        切不出来 / 归不齐 / 映射不上的部分，进 quarantine/
                生成 DecompositionPlan 的 reject 报告，人工处置
```

### 6.2 切分工具与手段

| 手段 | Blender 操作 | 适用 |
|---|---|---|
| 按材质槽切 | `separate by material` | 材质边界清晰的整栋（最常见） |
| 按连通域切 | `separate by loose parts` | 构件间本就分离的模型 |
| 按平面切 | `bisect` + `separate` | 台基/屋身/屋顶的大层分离 |
| 按选择集切 | 手工 / 规则标注 | 材质粘连的部分（如屋脊与瓦面同材质） |

> **现实预期**：AI 生成的整栋模型，材质槽质量参差不齐。**工序 ②③ 是全流程最容易失败的地方**，也是路线 B 成本远高于路线 A 的原因。因此：
> **能走路线 A 就走路线 A**；路线 B 只用于"必须有整栋整体性"的 hero 件。

### 6.3 插槽推断规则（`decompose/rules/`，按构件类型）

| 构件类型 | 推断插槽 | 规则 |
|---|---|---|
| 柱（`pillar`） | 底 `ground-foot`(-y) + 顶 `stack-up`(+y) | 底面中心 → 柱础；顶面中心 → 额枋/斗拱 |
| 柱础（`base`） | 底 `ground-foot` + 顶 `stack-up` | 上下同轴 |
| 额枋（`beam`） | 两端 `wall-line`(±x) | 端面中心，长度须为 `pillar_spacing_m` 整数倍 |
| 斗拱（`bracket`） | 底 `stack-up`(-y) + 顶 `roof-seat`(+y) | 底面中心对柱头/枋顶 |
| 瓦面（`roof`） | 沿檐口 `continue` + 与脊线 `ridge-point` | 重复阵列，`step_m` 由瓦宽决定 |
| 墙段（`wall`） | 两端 `wall-line`(±x) | 长度须为 `wall_module_m` 整数倍 |
| 台基（`base`） | 顶 `roof-seat`（承载）+ 侧 `wall-line` | 顶面水平 |
| 装饰（`ornament`） | `attach` | 单向挂接，允许非网格落点 |

### 7.2 装配清单生成

装配不是手工摆。三种生成方式：

| 方式 | 做法 | 适用 |
|---|---|---|
| **模板参数化** | 建筑模板（§8）填参数 → 自动铺柱网 / 斗拱 / 瓦面 | 标准形制（**主力**） |
| **脚本阵列** | 按 `continue` 插槽沿方向重复（栏杆、连廊、街墙） | 线性重复 |
| **手工摆放** | 在 Blender 里摆好后导出清单 | hero 建筑 |

## 8. 建筑模板与参数化

建筑模板 = **一份带参数的装配清单骨架**（`build/templates/`）。

```jsonc
{
  "template_id": "cn-ancient/tpl-hall-xieshan-double",
  "name": "歇山重檐大殿模板",
  "granularity": "L0",
  "params": {
    "bays":          { "type": "int",  "default": 5, "values": [3,5,7,9] },   // 开间数
    "bay_width_m":   { "type": "enum", "default": 4, "values": [3,4,5] },     // 明间面阔
    "story_count":   { "type": "int",  "default": 2, "values": [1,2] },       // 屋檐层数
    "bracket_grade": { "type": "enum", "default": "wupin", "values": ["qipin","wupin","sanpin"] }
  },
  "rules": [
    { "expand": "colonnade",  "count": "params.bays + 1", "spacing": "kit.grid.pillar_spacing_m" },
    { "expand": "bracket",    "at": "colonnade[*]", "asset": "cn-ancient.bracket.pingshenke-a" },
    { "expand": "bracket",    "at": "colonnade[first,last]", "asset": "cn-ancient.bracket.zhutouke-a" },
    { "expand": "tile-field", "along": "roof.eave", "step_m": 0.4 }
  ]
}
```

**收益**：万安城主殿（7 开间）与配殿（5 开间）是**同一个模板的两个参数组合**——不是两份装配清单。

> 模板本身也是**可复用资产**，但**不进 `kits/`**（它不是网格资产）；放 `gbe-studio/build/templates/`，其生成的装配清单投递到 assets 的 `assemblies/`。
> ⚠️ 待定：模板是否需要在 assets 侧也有副本（供 Web 端"按模板新建建筑"？）。当前裁决：**不需要**，Web 只读清单（清单是自包含的）。

> **转角件为什么是「墩」而不是「L 形墙」（批 1 实施裁决）**：`qiang-corner-a` 与 `balustrade-corner-a` 原设计为 L 形整件，实现时发现它在「底面中心轴心 + 插槽落 0.5 m 定位网格」两条约束下**不可自洽**——翼厚 0.5 m 时两翼中心线在 ±0.25，永远落不到网格上。一般化的结论是：**L 形转角件的翼厚必须 ≥ 1.0 m**（`2·snap_m` 的整数倍），而 1 m 厚的转角墙在美术上不可接受。故两者实现为**枢轴式节点件**（角墩 / 望柱，插槽落轴心），L 形交给装配清单表达——这反而更贴合粒度判据 2「结构可分离」：**L 形是装配结果，不是构件**。详见 CONVENTIONS §19.5「节点件接法」。

> **预算估算**：24 × 30 + 3 × 55 ≈ **885 credit** 建库（程序化 18 件不花钱）。
> 对比逐栋生成 25 栋 ≈ 1375 credit —— 但**别只看这一行**：§1.2(a) 的口径下 25 栋时生成 credit 仍高于逐栋（2385 vs 1375），回本靠的是复用带来的精修 / LOD / 材质免重做。见 §1.2 的警示框。
> **省钱的真正来源是那 18 件程序化构件**——它们把建库期的 AI 调用费压掉八成，且确定性可重建、不依赖平台与网络。

## 10. QA 与验收

### 10.1 构件级（出包门禁，CONVENTIONS §9 已列）

`granularity` 存在 · 模数对齐 · 插槽完备（L2+ 至少 1 个）· 面数在 tier 预算内 · 材质槽已声明 · 轴心/朝向/单位正确。

### 10.2 装配级（投递清单前，CONVENTIONS §19.5）

引用存在且 `published` · 插槽两端互认 · `direction` 反向 · `position` 重合（±1e-3 m）· 网格对齐 · **无几何穿插** · **承重链落地闭合** · 装配总面数在场景预算内。

### 10.3 建筑级（新增，本方案定义）

| 判据 | 目标 |
|---|---|
| **复用比** | 3 – 15（独特构件数 / 总实例数 的倒数关系，见 §4） |
| **LOD 链完备** | LOD0 ≤ 350k · LOD1 ≤ 90k · 远景代理 ≤ 12k，三级齐备 |
| **实例化收益** | 同形制第 2 栋的**新增几何**为 0（纯引用） |
| **可改性验证** | 替换 1 件构件（如青瓦→琉璃）后，装配结果正确且无需改清单 |

### 10.4 端到端 DoD（并入 CONVENTIONS §17）

至少 1 件构件具备完整 `sockets[]` 且通过网格对齐校验，并可被一条装配清单引用成功装配。

## 11. 风险与回退

| 风险 | 触发信号 | 对策 / 回退 |
|---|---|---|
| **形制不收敛**（本方案的核心赌注失败） | 批 2 验证点：新建一栋仍需 ≥4 件全新构件 | **回退**：放弃路线 A 的"全库复用"目标，改为"每类形制一套整体资产 + 仅拆 L3 装饰"——复用率下降但成本可控 |
| **AI 生成构件成功率低** | 批 1 中裸屋顶合格率 < 40% | 提示词迭代（沿用原型四段式）；仍不达标则改走路线 B 拆现有的整栋模型 |
| 整栋语义切分失败（材质槽质量差） | 路线 B 团块识别率 < 60% | 降低对路线 B 的依赖（它只负责 3 件 hero 件的局部）；必要时改为手工切分 + 记录配方 |
| 构件数爆炸 | 复用比 > 20 | 按 §4 判据合并（如额枋+平板枋合并为"额枋组"） |
| LOD0 面数失控 | 单栋 > 350k | 斗拱单独降级；远景强制走烘焙代理（不可关闭） |
| 插槽推断错误率高 | 装配校验失败率 > 30% | 插槽模板按构件类型固化（`decompose/rules/`），减少 AI 推断自由度 |
| 装配清单维护成本 | 改一件构件导致大范围重装配 | `used-by` 影响面分析 + 装配校验自动化（assets 侧已提供） |
